# 小程序一级页真实服务端数据对齐设计

**状态：已获用户确认，待用户审阅本文档后实施。**

## 目标和范围

以运行中的网页版 `http://127.0.0.1:5176/` 的四个一级页面为视觉和信息层级参考，将微信小程序的“工作区、任务、功能、我”对齐到同一产品结构。所有动态业务事实必须来自已存在的服务端接口；小程序不写入静态账号、任务、权限、额度、模型状态或虚构统计。

本次仅调整小程序前台的数据投影、一级页面结构和真实状态反馈。不新增服务端接口、不改变微信登录/绑定协议、不重做二级创作工作台，也不改动另一个脏工作副本 `server-main/miniprogram`。

## 运行前提

- 小程序继续通过 `Taro.request` 和现有业务令牌访问 API。
- API 源站来自私有环境的 `TARO_APP_API_ORIGIN` 构建注入，必须是已备案且已配置微信合法 request/upload/download 域名的 HTTPS 源站。
- `https://api.example.invalid` 是故意不可用的配置占位符。构建配置未注入真实源站时，页面必须明确显示“服务端未配置”，不得把失败解释为空列表。
- `127.0.0.1:5176` 仅用于查看网页版参考，不是小程序 API，也不可作为真机的服务端地址。
- 不读取、输出、写入或提交 `.env.development`、`project.private.config.json`、业务令牌、微信 code、AppSecret 或密码。

## 方案选择

采用“共享真实数据投影层”。页面只负责展示和交互；新服务层负责读取既有接口、识别各来源的数据形状、保存来源状态，并输出可展示的真实任务条目。

未选择“直接在任务页内并发请求四个接口”，因为该方案会继续把映射、状态推断和错误处理分散在组件中。也不新建服务端聚合接口：这会扩大为后端契约、鉴权和发布工作，超出本轮一级页面对齐范围。

## 数据边界

### 任务：四个真实来源的局部可用汇总

| 来源 | 既有接口 | 服务端事实 | 展示规则 |
| --- | --- | --- | --- |
| 剧本历史 | `GET /api/history` | `entries` 和其中的剧本/视频状态 | 保留“剧本”来源。仅在服务端明确返回视频数量和完成数量时显示进度。 |
| Agent | `GET /api/agent/tasks` | `tasks` | 保留“Agent”来源、真实标题和原始任务状态。 |
| 小说获取 | `GET /api/novel-fetch-workshop/tasks` | `tasks` | 保留“小说获取”来源和服务端书名/任务状态。 |
| 批量工厂 | `GET /api/batch-factory/v12/batches` | `batches` | 保留“批量工厂”来源和服务端批次状态。 |

加载使用 `Promise.allSettled`，而不是当前的 `Promise.all`。因此，一个来源 401、403、5xx、网络失败或返回无效形状时：

- 已成功的来源照常展示。
- 失败来源显示来源名称、真实错误摘要和“重试”操作。
- “全部”筛选包含每一个成功读取的任务；其他筛选只包含服务端状态能明确映射的任务。
- 全部来源失败时显示页面级失败状态和刷新操作。
- 全部来源成功但没有条目时显示“暂无真实任务记录”。

状态映射只能识别服务端明确的运行、失败、完成语义。缺少 `status`、无法识别的新状态、或者某来源没有该字段时显示“状态未返回”，不默认成“已完成”。缺少标题、时间、进度也分别显示为空值或“服务端未返回”，不填入“未命名任务”“已同步”或 100% 进度。

列表排序只比较服务端返回且能解析的时间；无法解析时间的条目保留来源内的服务端顺序。不会用浏览器当前时间伪造任务时间。

### 我：账号中心的真实投影

个人页继续请求 `GET /api/member/me`，头像仍使用 `POST /api/member/avatar`。第一屏只展示响应中实际存在的：头像、显示名/用户名、角色、团队、AI 服务授权、授权范围、额度和用量。

现有“创作等级”由本地 Token 阈值推导，并非服务端正式等级。为符合本轮真实数据要求，这一区域保持网页版相近的视觉尺寸，但改为“本月用量”：直接展示 `usage.month.totalTokens` 和服务端返回的可用额度。只有以后端返回正式 `level` 字段时，才显示“等级”和等级进度。

服务端未返回资料时显示“无法读取当前账号资料”和重试；不显示“一战”“username”“0 Token”或“未授权”等默认身份。角色可见的菜单仍由服务端角色/能力字段决定；没有可验证后端数据的安全、治理或后台入口不得借用通用个人资料来声称已经读取成功。

### 工作区和功能：区分导航元数据与业务事实

模块名称、图标和跳转路径是客户端导航定义，不是用户数据，可以保留。它们不能被写成“当前服务端任务”“服务端正在使用”之类的断言。

“继续工作”只有在 `/api/history` 返回可恢复的真实剧本记录时才展示具体服务端条目；无记录时使用明确空状态。本机保存的最近打开模块可以继续作为操作偏好，但文案必须是“本机上次打开”，不冒充跨设备或服务端同步结果。

功能页按网页版的一行一个入口的层级改造。入口若因服务端 403 或能力不足无法使用，应展示真实的拒绝/不可用状态，不在客户端通过固定角色猜测后伪装为可用。

## 页面状态和交互

每个读取真实数据的区域都有四种独立状态：加载中、真实内容、真实空结果、读取失败。失败状态提供当前区域的重试按钮；不会以成功卡片掩盖失败。

手动刷新任务页时重新读取四个来源。刷新期间保留最后一次成功的条目，并给出刷新中状态；首次进入尚无任何成功数据时显示骨架屏。退出登录、401 或业务令牌失效继续沿用现有会话清理和账号绑定流程。

## 模块边界

- `src/services/api.ts`：继续是唯一的 Taro 请求、授权头和 HTTP 错误边界；不改为网页的 `fetch`、Cookie 或 `localStorage` 会话。
- 新的任务投影服务：解析各来源，暴露数据、来源状态、刷新函数所需的稳定类型；不在这里生成业务内容。
- 任务页面：渲染筛选、来源提示、列表、进度和重试；不认识 HTTP 响应形状。
- 个人、工作区、功能页面：只消费各自验证过的投影；保留微信原生页面/Tab 路由。

## 验证计划

先补失败测试，再实现：

1. 单元测试四个来源的正常条目、未知状态、缺失时间、缺失标题、真实进度和来源排序。
2. 单元测试一个或多个来源失败时，成功来源不丢失，失败来源可重试。
3. 单元测试 `api.example.invalid` 未配置状态不会显示为空数据或成功内容。
4. 单元测试个人页不再用静态姓名、Token、等级或授权状态填补缺失服务端字段。
5. 运行 `npx tsc --noEmit`、`npm test` 和 `npm run build:weapp`。
6. 在微信开发者工具中，以已绑定账户验证四个来源的实际请求、加载、空、局部失败、401 回绑定、头像上传和 Tab 安全区。该步骤需要现有私有配置和用户已登录会话，但不记录令牌或敏感响应。

构建成功、页面打开或 HTTP 200 只证明一部分链路。完成验收必须同时证明：正确构建源站、已绑定账号、每个实际接口的服务端结果，以及小程序内相应的加载/空/失败/重试展示。

## 不在本轮范围内

- 新建或重构后端聚合 API。
- 把网页 DOM、Cookie、Drawer 或本地存储方案搬进 Taro 小程序。
- 伪造视频、任务、权限、模型、团队、使用量或成功状态。
- 改动 `server-main` 中用户尚未提交的代码，或将该目录的脏改动一并提交。
