# 批量测书第一批修复设计：正文保护

日期：2026-11-27。设计待用户审阅；本文不代表业务修复已实施。

## 目标和范围

延续《批量测书：源码对照、链路问题和简化建议》的推荐路线，第一批只处理会污染或丢失正文的路径，为后续统一执行入口提供可靠基础。

完成后应满足：对 AI 正文应用规则只处理真实文字；正文保存失败不损坏之前成功的正文；清理和保存同时发生时不删除新正文；删除或提交结果不明确时保持可恢复的证据。

后续批次分别处理正文加载与摘要一致、执行去重与停止、重试预算与按需扫描。本批不更换抓书上游、不引入浏览器、不调整模型、不增加真实付费请求，也不修改无关功能。

源码基线：设计核对时 v88 HEAD 为 `3f06c3d7126103d36152ee1a4b07ecac0a3fb0b0`。工作区存在其他任务改动，实施前重新核对，不覆盖它们。

## 路线选择

1. 只把 TOS 删除移到 SQL 后面：改动小，但固定地址仍允许新保存覆盖旧对象，SQL 回滚与结果未知也未解决，不采用。
2. **独立对象地址、数据库切换引用、延后回收**：改动集中，能明确区分旧正文和新正文，采用。
3. 整体更换正文存储或重写系统：涉及大量迁移，无法为这几个具体问题带来相称收益，不采用。

## 规则只处理文本

沿用现有正文存储和加载能力，增加明确的版本正文读取规则：优先读取独立正文记录；不存在时才接受兼容字段中的字符串或明确的 text 字段。真实读取失败时返回该版本失败，不把数据库或 TOS 错误伪装成无正文。

禁止 `fmt.Sprint` 将任意版本对象、布尔值或状态转为正文。版本信息可以保留，但不能参与文本规则处理。

每个版本先计算处理结果，再保存正文；保存成功后才更新该版本的引用与成功记录。保存失败不把该版本标为成功。批量结果按书籍和版本报告成功、失败、跳过，避免失败被统一成功提示掩盖。前端只增加必要的结果提示，不重做页面。

本批保证不污染文本和不虚报保存成功；正文与整个任务摘要的统一更新由下一批承接，不将跨版本批量处理宣称为全有或全无事务。

## 新正文不覆盖旧对象

TOS 新写入使用包含随机写入标识的独立地址，保留账号隔离、书号和版本目录。即使内容相同，两次独立写入也不得复用可被失败处理删除的地址。旧的固定地址仍可按数据库记录读取，不批量搬迁现存正文。

保存顺序：

1. 生成本次独立地址，写入新对象。失败返回错误，保留旧引用。
2. 在 MySQL 短事务中锁定对应正文记录，读取当前引用，写入新引用、指纹、字数与递增版本，同时登记旧对象待回收记录。
3. 事务提交成功，返回本次保存的准确版本信息；不要在事务后无条件重读其他并发保存的结果当成本次返回。
4. 写入事务或提交报错时，不立即删除本次对象。提交响应丢失时，数据库可能已经成功，直接删除会破坏新引用。对象留存并记录脱敏诊断，等待确认。

本批不建立全桶扫描或自动删除未知对象。新对象写入成功、数据库引用未成功的情况可能暂时留下孤立文件；优先保护正文，记录数量并在后续核对后回收，不能静默承诺没有额外存储占用。

## 清理先确认引用，再回收对象

手动容量清理、过期清理和 DeleteBody 共用同一安全顺序，不只修其中一个入口。

1. 候选查询携带精确的正文版本、对象地址和可释放时间。
2. MySQL 短事务内重新锁定并核对候选。条件已变化或正文重新保存则跳过，不能删除对象。
3. 满足条件时移除对应正文记录与引用，登记精确对象地址的待回收记录，事务提交后才允许物理删除。
4. 回收只处理已确认提交的待回收记录；失败保留记录，下次继续。删除成功只更新对应记录，不回写用户的新正文。

待回收信息持久化在 MySQL，以便进程崩溃后恢复；它是对象引用生命周期记录，不另建一套业务执行队列。实际派发沿用已有调度及 Redis 能力，不新增独立服务。记录至少包含对象地址、账号、书号、版本、登记时间、允许删除时间、状态、尝试次数和最后错误。

新增对象地址永不重新用作后续写入地址，因此待回收旧对象不会成为新正文。回收前保留宽限期，避免正在读取旧引用的请求立刻失效。

历史固定地址默认保留，不在本批自动物理删除；先证明不存在旧写入者、活跃引用和混合运行版本，再安排专门回收。这个选择会暂时减少空间释放量，页面需区分“已移除正文记录”“对象待回收”和“历史对象保留”，不能假报空间已释放。

新增持久化记录使用项目现有 Goose 迁移方式。上线顺序为迁移先行、程序后行；回退程序时不删除已有记录或对象。回退旧写入代码期间暂停对象回收，防止固定地址再次被使用后遭到删除。

## 职责边界

| 部分 | 负责什么 |
|---|---|
| 规则处理入口 | 读取明确文本、逐版本计算结果、报告失败 |
| MySQL 正文存储 | 原子切换引用、递增版本、登记待回收信息 |
| TOS 存储适配 | 对精确地址写入、读取和删除，不猜测任务状态 |
| 回收处理 | 在宽限期后删除已确认退役的新格式对象，失败保留记录 |
| 前端 | 显示实际处理结果和待回收状态，不决定正文是否可删除 |

## 验收

先把归档目录中三条已失败的诊断转为正式回归测试，确认修复前失败、修复后通过：规则不写入版本对象字符串、保存失败保留旧对象、并发重新保存不被清理误删。

另外覆盖：

- 独立正文、旧字符串字段、带 text 的版本信息对象，都读取正确文本；仅有状态信息时不生成伪正文。
- TOS 写入失败、SQL 写入失败、提交结果未知，均不删之前正文或本次可能已生效的正文。
- 两次并发保存使用不同对象地址，各自返回正确版本；已有引用内容可读。
- 手动、过期、直接删除三种入口均在数据库确认前零对象删除。
- 清理条件已失效时零对象删除；回收失败、进程重启可继续处理同一精确地址。
- 历史固定地址不被自动回收；其他账号对象不受影响。
- 接口部分失败时前端显示实际数量，不统一提示全部成功。

用模拟 TOS 和隔离 MySQL 验证故障与并发，不对真实桶进行破坏性测试。完成必要 Go 测试、相关前端测试及构建后，依项目要求构建 Go embed，先在隔离端口验收。确认本地 4001 活跃任务后择机切换，不中断已有付费任务；生产发布另按已有授权执行。

## 自审结果

范围限定为正文保护；已明确旧对象兼容、提交结果未知、并发、回收失败和回退行为。数据可靠性优先于立即释放空间；未承诺速度倍数或 CPU 降幅。第二批的统一执行、去重和重试预算不借本批扩散实施。
