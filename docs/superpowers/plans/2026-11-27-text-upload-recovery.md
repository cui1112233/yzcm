# 文本合集超时与断点续传修复计划

> 执行方式：沿用当前 v88，由当前聊天顺序实现和验证；不另建分支，不打断在途任务。

**Goal:** 已有文字页保存后能继续整理和上传；重试保留图片和回执，不重复发布成功合集。

**Architecture:** 沿用 Workflow、阶段表和发布回执，增加可选阶段预算；阶段切换更新上下文和错误归属。只有本地渲染/校验/整理的暂时故障有限次续跑；未知模型/上传结果不自动重发。

**Tech Stack:** Go、MySQL、现有 Redis/TOS、Go embed。

## 已确认设计

- 后端 workflow.go：处理/分页/校验/整理各10分钟，渲染与上传各45分钟；阶段预算受原书的暂停/取消约束，不重新创建后台循环。未设置预算的调用方保持原上下文行为。
- httpapi 配置：初始化读取10分钟；进入工作流后使用原书上下文，每个回调按当前阶段上下文读取、保存，不引用上阶段已取消的上下文。
- 自动续跑仅适用 text_render/text_validate/text_collection 的超时、暂时网络错误、乐观锁冲突；最多3次，退避30/60/120秒，计数持久保存在原任务中。text_process可能涉及模型，text_publish可能已提交，不能凭超时盲目重发。原回执待确认流程保留。
- 状态在读取合集前先进入 text_collection，校验完成后的数据库错误不能再显示成校验失败。
- 本次恢复只针对已完成图片、当前未确认成功的合集。已成功的网络回执跳过；未确认的先读取状态，续传保持原合集及请求身份。不执行强制重生成或强制再次上传。
