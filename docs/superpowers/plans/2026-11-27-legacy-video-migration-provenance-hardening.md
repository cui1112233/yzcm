# 历史视频凭据来源加固实施计划

## 目标

关闭 API 配置 Task 2 最终复核的 R5-I1：旧文件首次暂不可见时，数据库历史视频凭据不得被永久提升为正式可执行配置；旧文件随后恢复并携带冲突凭据时，两份来源都必须进入可审计、可逐条恢复的隔离区，运行时不得使用任意一把旧 Key。

## 全局约束

- 直接在 `v88` 上实施，不创建分支或 worktree；只提交本任务文件，保留共享工作区其他改动。
- 必须先写自动化回归测试并确认它在修复前因 R5-I1 正确失败，再改生产代码。
- 不访问外部供应商，不使用真实 Key；凭据只使用合成测试值。
- 不改共享 4001，直到本任务独立复核通过并进入统一可见里程碑。
- 不改变已经通过的行为：两源首次同时可见时的冲突隔离；相同 Key 合并；已有正式视频行优先；逐条恢复及审计；迁移失败回滚；无适配器 YZCM 视频不可执行。

## Task 1：持久记录迁入来源并完成延迟核对

### 失败用例

在真实 MySQL 集成测试中构造：

1. 账号已有一个无关的正式 v3 文本模型。
2. 数据库旧 `videoProviders` 保存视频配置 A 与合成 Key A。
3. 相同旧文件暂时不可见，第一次 `GetConfig` 触发数据库来源迁移。
4. 旧文件恢复，`settings.videoProviders` 保存相同提供方、模型、地址但合成 Key B。
5. 新建 Store 冷启动并再次读取。

修复前测试必须证明运行解析仍返回 Key A。修复后必须断言：

- 该视频行不可执行，运行解析不返回 Key A 或 Key B；
- 数据库来源和文件来源各有一条独立加密隔离证据；
- 两份证据可通过现有正式会话逐条恢复并产生审计；
- 清理状态只有在来源核对和原件清理都完成后才结束；
- 再次冷启动结果保持不变，不能重新提升任一旧 Key。

### 实现边界

- 在持久配置中明确区分“用户原有正式视频行”和“由未完全核对来源的旧配置暂存迁入的视频行”。
- 当旧文件尚未完成首次核对时，暂存迁入行不得被运行解析当成正式行。
- 旧文件恢复后，用持久来源信息重新参与 `reconcileLegacyVideoCredentials`；冲突时归档数据库与文件两份原始凭据，禁用暂存行。
- 来源核对成功后应清除仅用于迁移的内部标记，避免泄漏到受限 API 响应。
- 优先复用现有冲突归档、加密、审计和清理机制，不另建平行恢复系统。
